# ノウハウ集: 確認のしかた・守ること・失敗と直し方

キャラを作る途中で「見たつもりで、見えていなかった」「直したつもりで、別の所が崩れた」出来事から来た決まりを、話題ごとに並べてある。手順そのものは `WORKFLOW.md`。
文中のキャラ名（`kurage`・`tomari02`・`pink02`・`neon` など）は、開発中に作ったキャラ（このリポジトリには入っていない）。`kurage02` は同梱の手本。

- うまくいった**手順**は `WORKFLOW.md`（工程表・章・合格の目安）へ。**なぜそうするか・何を見落としたか**は、ここへ。1 行に、決まりと、そのもとになった出来事を書く（出来事が無い決まりは、守られない）。
- 作り方を変えたら、専用の章を足すだけでなく、**工程表（`WORKFLOW.md` の段階 0〜8）・`MASTER_PROMPT.md`・ひな形（`chars/_template`）・合格の目安**の 4 か所を直す。指示文 1 つで通したとき、その作りになるように（キーの形の手順が、専用の章にしか無く、通すと古い作り方になっていたことがある）。
- 試しただけ・確かめていない物は、そう書いて、成功した手法と混ぜない。値には、**どう決めたか**（人が動かして決めた / 基準画像に合わせて測った）と、**確かめた範囲**を書く。

## 0. 品質の基準（作っていて分かった、見る人の目）

| 基準 | もとになった出来事 |
|---|---|
| 目標は「崩れていない」ではなく、「元の絵のキャラに見える」「表情豊かに、ぬるぬる動く」。AI で簡単に作れる 60 点ではなく、人が作る 100 点を超える 120 点 | 全項目 ok のモデルが、元の絵と並べると別人だった（60 点） |
| 絵を切り替える動きは、ガクッと止まって見える。絵は入れ替えず、形を変えてつなぐ | 差分シートのコマを切り替えたまばたきが、前より悪く見えた → キーの形（変形でつなぐ） |
| 感情の言葉で頼んだ目と口は、わざとらしく見える | 「にっこり」と頼んだ目（⌒）と口（深い U 字）は使えなかった → 顔のどこがどう動くかで書く |
| 真横で、まつげは顔の輪郭の外へ出ている方が自然。白目や瞳は外へ出さない | まつげが輪郭の中に収まって、切れて見えた → `tune.lash` |
| 最初に動かして見たときに気づかれる崩れがある: 首が二重、斜めいっぱいで鼻と口の位置が崩れる、横向きで口があごのしゃくれた形、まつげが髪の上 | → `neck_clean`・`tune.faceFit`・`tune.mouthFit`・`lashOver` 0。どれも、止めた正面の絵では見えなかった |
| 「口が不自然」は、形ではなく、顔の中での位置の問題のことがある | 口の形だけを直しても「まだ不自然」だった → 目・鼻・口・あご先の位置関係を、目安の数字に合わせた（`tune.eyeFit`・`tune.headTilt`） |
| 見た目の良し悪しがキャラによる所は、数字で合否を決めず、絵を見て判断して決め、決めたやり方と理由を伝える（聞き返さない） | 奥の目が輪郭をまたぐのは、キャラによって良し悪し |

| 目つき・構図・等身は、元の絵に忠実に | 基準画像で目つきが甘くなった。元の絵の構図のまま、顔を正面に起こすだけで描かせ直したら合った |
| 表情で、口の位置と大きさを動かさない。髪は、細い毛束の寄せ集めにせず、少数の大きな房で。パーツの質を最優先 | どれも、そうしなかったときに、ずれて見えた・まとまりが無く見えた |
| 起動した処理（撮影の Chrome・サーバー）は、終わったら確実に落とす。消せない一時ファイルの原因調べに固執せず、作業を進める | 裏で動き続けた処理で、PC が重くなった |
| 撮影は、チェックの質を落とさずに軽く。止めた絵は 9 方向（正面・上下左右・斜め 4 方向）で足りる | 撮影のたびに PC がかなり重くなった |
| 成功した手法は、そのつど文書へ。ノウハウの蓄積が、いちばん大事 | 同じ失敗を、次のキャラでくり返した |
| 画面の文字（タイトル・見出し）に、他社の製品名を出さない | — |

## 1. 確認のしかた（見落としを防ぐ）

どれも、「見たつもりで、見えていなかった」出来事から来ている。

- **「不自然」と言われたら、そのパーツだけを拡大せず、顔の全体を並べて見る。** 口が「しゃくれて見える」を、口の拡大で形だけ直したら「まだ不自然」と言われた。元は、目・口・あご先の位置関係だった（髪なしの顔の全体を、9 方向で、同じ縮尺・同じ位置で並べる。数字は `partsgen/tools/ref/probe.mjs`）。
- **形を直したら、位置も確かめる。** 前の「味付け」は、たがいに打ち消し合っていることがある（口角を手前へずらす味付けが、口の位置の出すぎを隠していた。形だけ直したら、口が奥のほほへ寄った）。
- **顔のパーツの位置を、目安の数字に合わせたら、このキャラの絵で、輪郭・髪との関係が崩れていないかを、拡大した絵で見る。** 目安の数字が合う顔と、キャラの絵は、顔の幅に対する目の大きさが違う。目・口・あご先の「位置の数字」を目安に合わせ、縮小した絵で「崩れなし」としたが、斜め下で、奥の目が輪郭を 53 画素越えていた（`partsgen/tools/ref/eyeedge.py` と、髪なし・髪ありの拡大）。
- **基準画像との見比べは、同じ縮尺・同じ位置で並べる**（`partsgen/tools/fidscale.py`。目のあたりは `--box`）。`PY fidelity` の拡大は縮尺がそろわず、髪飾りが 1.5 倍大きいこと、横髪の房が目尻のはねを隠していることに、気づけなかった。位置合わせの確認画像は、描かせた絵どうしを比べるので、基準からのずれには気づけない。
- **目と口は、zoom 7 まで拡大して見る。閉じた目・半目も。** 縮小した一覧では、縞・はみ出し・ちぎれ・閉じた目の下のしみ・二重の線の切れ端・まつげの二重写りは、見えなかった。
- **動きは、コマを刻んで、数字でも見る**（`partsgen/tools/ref/seqshoot.py`）。止めた絵を 0.5 秒おきに並べても、閉じる速さのむらや、絵の飛びは見えない。
- **向きは、斜めいっぱいの 4 方向まで見る**（`yaw=±30&pitch=±25`。画面の 9 方向ボタンと同じ姿勢。髪あり・髪なし）。左右だけ・上下だけの絵では、鼻と目・口のぶつかりも、奥の目と輪郭も、見えない（動かして見てもらうまで、気づかなかった）。
- **口の形は、左右いっぱいで、開いた口と、表情の口を全部見る。** 閉じた口の線だけを見ていて、開いた口の底が向いた側へ突き出るのに、気づかなかった。
- **首まわりは、髪ありで、境目を 5 倍に拡大して見る。** 縮小した一覧では、えりの中の赤い線の切れ端も、首とえりのすき間も、見落とした。
- **目安の数字に合わせる動きは、作る前に、同じ姿勢での目安の値を確かめる。** エンジンの中の目安の値も、向きの上限を変えたら、確かめ直す（鼻と口の上下の滑りは、上限 5°のころの味付けで、16°・28°では崩れた）。
- **エンジンの「立体に見える」味付けは、向きの上限が小さかったころの値。上限を広げたモデルでは、1 つずつ、実際の形と、目安の数字で確かめる。** 上下の滑り（`faceFit`）、口の左右の伸び縮み（`mouthFit`）、目と眉の奥行き・口を余分にずらす量（`eyeFit`）は、どれもこれだった。まだ確かめていない物: 鼻の左右の伸び縮み（`nose` の `asym` 1.85。右を向くと、鼻のハイライトが細い線になる）、目・眉の幅の変わり方（`zx`。奥の目は、強めに縮めている）、輪郭の奥のほほのふくらみ（`bulge`）。
- **「基準画像と同じ描き方」でも、動かすと不自然なことがある。** まつげを髪の上に重ねる（基準画像が、目尻のはねを髪の上に描いている）と、横を向いたとき、目にかかった横髪の上に、まつげがまるごと乗って見えた。止めた正面の絵が基準に合うことより、動かしたときに、物の前後が合っていることを優先する。
- **見た目の良し悪しがキャラによる所は、数字で合否を決めない。** 自然に見えるやり方を、絵（等倍と拡大）を見て判断して決め、決めたやり方と理由を書く（奥の目が輪郭をまたぐ、など）。
- **画素で比べられるのは、向きを指定して止めた絵だけ。** デモの絵は、撮るたびに、傘のふちと髪のそよぎが少し変わる（同じモデル・同じ時刻でも、画素の 0.1〜4%）。前後は、並べた絵を目で見る。向きの指定が無い絵（`yaw=` も `pitch=` も無い）も、自動の視線・まばたきで変わるので、正面にも `yaw=0` を付ける。
- **確認していないことは「確認していない」と書く。** 組み立てただけで、目では見ていない絵も、そう書く。
- **ユーザーが「動かない・効かない」と言ったら、その人のブラウザの画面で確かめる**（ブラウザを操作できるエージェントの道具があれば、それで。無ければ、画面を見せてもらう）。撮影用の Chrome は、毎回まっさらなので、ユーザーの画面と違うことがある（`neon`: 母音の口の形のスライダーが、撮影では効くのに、ユーザーの Chrome では効かなかった。後から読み込む `keyshape.js` だけが、前の版のまま使われていた）。
- **URL の指定で開いたときと、画面のボタンで選んだときの両方を確かめる。** URL に `mode=camera` を付けて開くと、表示は「カメラで追従中」なのに、動かし方はマウスへ戻っていた（起動時に動かし方を 2 回設定していて、カメラの準備が 2 重に走った。ボタンで押せば正常だったので、気づかなかった）。`uicheck.mjs` が、テスト用の偽のカメラで、両方を確かめる。
- **画面のスライダーを足したら、動かして形が変わることを、画面の確認（`uicheck.mjs`）で確かめる**（`neon`: 母音の口の形のスライダーは、キーの形の口には、前から効いていなかった。`uicheck.mjs` に、「あ」を選んで開きを最大にする確認を足した）。
- **つり目で、瞳が上まぶたの下へ入り込む絵柄は、瞳の高さを測って合わせる**（`iris_dy`）。基準画像と同じ縮尺で並べ（`fidscale.py --box`）、瞳孔の下の端と、瞳の色の境目の高さで比べる。目分量の −33 は上げすぎで、−20 が合った（`neon`）。道具は、瞳を「白目の開きのまん中」に置くので、このような絵柄では低くなる。

## 2. 作るとき・直すときの決まり

- **本番のモデルと設定は書き換えない。** 試すのは `<キャラ名>_test`（`chars/<キャラ名>_test` と作業フォルダ・モデルを写す）か、URL の指定（`eyeFit=0` など。本番を書き換えずに、前後を撮れる）。見比べてから、本番へ入れる。
- **新しい動き・処理は、「書かなければ（0 なら）前と同じ」の項目にする**（`tune.browBounce`・`faceFit`・`mouthFit`・`eyeFit`・`headTilt`、`neck_clean`）。既存モデルを変えない。ユーザーも、調整パネルで 0 と 1 を見比べられる。
- **エンジンや道具を変えたら、`kurage02`（と、自分で作ったモデル）を前後で撮って、画素で比べる**（`regress.py shoot` → `compare`。同じ描画方式で撮った絵どうしで）。変える前のエンジンは `git show HEAD:js/avatar.js > js/_base.js` と、それを読む `_base.html` で撮る（終わったら消す）。
- **絵は入れ替えない。形を変える。2 枚の絵を、止めた値で半々に溶かさない**（まつげの絵は、いつも 1 枚。切り替わる所の短い間だけ重ねる。半々に溶かすと、帯から上へ出る毛が、二重に薄く見えた）。
- **描かせた絵は、指示どおりの大きさ・位置にならない前提で、測って合わせる**（シートのコマの開き、目の高さ、房の位置と長さ、髪飾りの大きさ。どれも、指示とずれていた）。
- **つながっている物は 1 枚で描かせる。分けて描かせた物は、元と形が合わない**（傘の垂れを分けて描かせたら、傘から離れて浮いた → 傘は 1 枚のまま揺らす）。
- **改行は LF。`.bat` と `.ps1` だけ CRLF**（`.gitattributes` で決めてある）。cmd.exe は LF の `.bat` を読み違えることがある。`.bat` の中身は英数字だけにする（日本語を入れると、コマンドプロンプトが読み違えた）。
- 長い Python・JS・文書を、シェルに直接書かない（引用符・バッククォートで失敗する。ファイルに書いてから実行）。道具の出力は、どれも UTF-8。
- **Git Bash の `sed -i` は、CRLF のファイルを LF にしてしまう**（起動用の `.bat` が LF になり、差し替えも効かなかった）。`.bat` を機械的に書き換えるときは、python で読んで、改行を CRLF に戻して書く。
- **硬い小物（ヘアピン・ツノ・ヘッドホン・ピアス）は、点ごとに頭の面へ沿わせない。1 個ずつ「固い板」として動かす**（付いている点の動きだけを、全体に一次の変換として掛ける。`WORKFLOW.md` の「硬い小物」）。前は、髪飾りの全部を 1 つの基準点で動かし、ヘッドホンを顔の面に沿わせていて、髪とずれ、形がゆがんだ。
- 確認のブラウザは Chrome か Edge。Python は `.venv`（`-I` 付き）。PowerShell のスクリプトは UTF-8（BOM 付き）。
- **コミットは、ユーザーの指示を受けてから。** `git add` が `.git/index.lock` で止まったら、ロックの日付と大きさ、動いている git を見る（前の日の日付・0 バイトの消え残りだったことがある。消してから入れた）。

## 3. 絵を描かせるとき

手順と、絵ごとの見る所は `WORKFLOW.md`。ここには、考え方だけ。

- **パーツ 1 つ 1 つの質が、モデルの質を決める。難しい切り抜きはせず、きれいに作れる絵を描かせる。** 粗を見つけたら、しきい値をいじり続けず、そのパーツを清書させる絵を足す。
- **感情の言葉（「にっこり」）で頼まない。顔のどこが、どう動くかで書く。**
- **同じ絵師が 1 枚に描いた差分として、シートで描かせる。** 閉じた目を 1 枚だけ別に描かせると、開いた目と別物になる（まつげが細い、形が違う）。
- **目のシートには、瞳を描かせない**（白目だけ。まつげと白目を、色で分けられる。瞳と白目は別のパーツなので、どの状態でも視線が動く）。
- **案を 2〜3 枚描かせて、選ぶ。** 好みの判断でも、止まらずに、こちらで選んで進め、選んだ理由と、選ばなかった案を残して、あとで見せる。
- **見本（描かせる絵に添える絵）には、描かせたい物だけを写す。** 別のレイヤーの物が写っていると、描かせた絵にも入る（首が二重になった）。
- **色を合わせる先は、いつも基準画像（`00_base`）。** 描き直すたびに、色は少しずつずれる。指示文の色の言葉は、測った色に合わせて書く。

## 4. 撮影と、PC の環境

- **撮影は、チェックの質を落とさずに、PC に負担をかけない。** 止めた絵は 9 方向（正面・上下左右・斜め 4 方向）を基本に、大きめに撮って、拡大は切り出しで見る。連続撮影は、動きの段を確かめるときだけ、範囲を絞って。64 姿勢の回帰は、エンジンや道具を変えたときだけ。
- **道具は、GPU で描き、優先度を下げ、Chrome 2 つで撮る**（前は、ソフトウェア描画で 4 つ並べて、全部の CPU を埋めていた。同じ 9 枚が 37.6 秒・96% → 6 秒・38%）。終わりの行の「その間の PC 全体の CPU」が 30% 前後なら、ふつう。**GPU とソフトウェア描画の絵は、ふちの画素が違う。画素で比べる 2 組は、同じ方式で撮る**（`AVATAR_SHOOT_SW=1` で前の方式）。
- **撮影は、同時に走らせない**（画像生成は、同時でよい）。**始める前に、何分ほどかを一言。終わったら、起動した処理が残っていないことを数えて、伝える**（Windows: `powershell -NoProfile -File partsgen/tools/procs.ps1`。スクリプトの実行が止められている PC では `-ExecutionPolicy Bypass` を足す。ユーザー自身の Chrome は、落とさない）。
- **後始末・再試行には、必ず上限時間を付ける。** 「消えるまで繰り返す」作りにして、道具が 10 分以上 CPU を使い続けた。エージェントの「処理を止める」機能は、子の node・python を止めないことがある（止めたあとも、数える）。
- **環境の問題（権限・セキュリティソフト・一時ファイル）の原因調べは、1〜2 回で切り上げて、避ける作りにする。** セキュリティソフトによっては（作った PC で起きた）、Chrome のプロファイルを、ブラウザー以外のアプリが消すのを拒否する（1〜2 分動かしたプロファイルが対象）。保護は回避しない。撮影用のプロファイルは、作っては消さず、`%LOCALAPPDATA%\keshin2d_work\_chrome_prof\`（環境変数 `KESHIN2D_WORK` があれば、その中）を使い回す（`partsgen/tools/chromeclose.mjs`）。Chrome の処理の優先度も、道具から、あとからは変えられなかった（原因は調べていない）。
- **確認に使った一時のスクリプトと姿勢の一覧は、エージェントの一時フォルダではなく、そのキャラの作業フォルダ（`PY status <キャラ名>` に出る場所）の `_verify\tN\` に置く**（一時フォルダは、途中で消えたことがある）。くり返し使う道具は、`partsgen/tools/` へ入れる。
- ブラウザは、古いエンジンを覚える。**強制更新（Ctrl+F5）でも、後から読み込む js（`keyshape.js`）は、前の版のまま使われた**（`python -m http.server` は、キャッシュの指定を付けない）。だから、起動スクリプトは `tools/serve.py`（キャッシュさせない）で配り、`index.html` と `avatar.js` は、js を読むたびに `?v=時刻` を付ける。調整の値は、ブラウザに保存した値が、モデルの初期値より優先される（新しい項目は、モデルの初期値で始まる）。

## 5. 症状 → 原因 → 直し方

章ごとの落とし穴は、`WORKFLOW.md` の各章の「落とし穴」（キーの形・揺れ物・髪・全体）。ここには、`kurage02` と、開発中の `pink02`・`neon` を作る途中で見つけた物を、まとめて置く。

| 症状 | 原因 | 直し方 |
|---|---|---|
| 目のキーが取れない | 輪郭線・耳の線が「濃いまつげ」に入り、目の塊がコマのふちにつながった | 輪郭線は濃くても赤茶（R が B より大きい）。濃いまつげ（紫がかった黒）と、色で分ける |
| 下まつげ・二重の線が、コマごとに有ったり無かったり | 赤茶の線は、輪郭線とつながるかどうかで取れ方が変わる | キーの絵は、濃いまつげだけ。下まつげ・二重の線・目尻の線は、決まったコマから 1 枚ずつ |
| 閉じかけの目に縦の縞 | 閉じたキー（開きが 0）の絵を、開いた目へ変形すると、帯の下のふちの 1 行が、開きいっぱいに伸びる。白目を S 字で縦に詰めると、細い所でメッシュが折り返す | そのキーで開きが無い列は、伸ばさない。白目は、まっすぐ詰める |
| 目尻・目頭に白目がはみ出す | 白目を「開いた目からの差」で動かしていた | 白目の上下のふちを、キーの線そのものに合わせる |
| 半目で、帯から上へ出る毛が、二重に薄く見える | となりのキーを、半々に溶かしていた | 線は連続のまま、絵だけ、区間のまん中で入れ替える |
| 閉じる速さが、最後だけ速い | 途中のキーを、名前の数字の位置に置いていた（絵の実際の開きは、指示と違う） | キーの位置を、絵の開きから決める |
| 目が小さく・丸く見える | 描かせたシートの目が、基準より高く・開いて描かれた。横髪の房が、目尻のはねを隠す | `key_eye_dy`・`key_eye_rest` を、同じ縮尺の絵で測って決める。房を少し外へ |
| 後ろ髪の外側の房と毛先が欠けた | 房の目印（多角形）が小さかった | 目印を、房の全体を覆う大きさに |
| 髪飾りが大きい・ずれている | 別に描かせた絵が、基準画像の 1.5 倍に描かれていた | 基準画像と同じ縮尺で並べて測り、`place` で手置き |
| 眉が見えない | 髪と同じ色 | `browTint`（髪の上に重ねる眉を濃くする） |
| 首が二重に見える | 体の絵に、首の輪郭線の切れ端が残る。首とえりの境目に、明るい線と色の段 | `neck_clean`（服が赤・肌色のキャラでは使わない） |
| 斜めいっぱいで、鼻が、目や口にぶつかる | 鼻と口だけ、目の 1.6〜2.2 倍 上下に滑る味付け | `tune.faceFit` |
| 横を向くと、口が、あごのしゃくれた人の形 | 口の手前の半分を伸ばし、奥の半分を詰める味付けが、30°では約 3 倍の差 | `tune.mouthFit` |
| 口の形を直しても、まだ不自然 | 位置の問題。目の動きが足りず、あご・口・鼻だけが先へ出る。斜め下では、ねらいと逆向きに傾く | `tune.eyeFit`・`tune.headTilt`（顔の全体を 9 方向で並べる） |
| 斜め下で、奥の目が輪郭をまたぐ | 下を向くと、目が、顔の中で下へ滑って、輪郭の細い所まで下りる。そこへ `eyeFit`・`headTilt` が重なる。このキャラは、顔の幅に対して目が大きい | **見せ方は、まだ決めていない**（案: 奥の目を輪郭で切る、下向きのときだけ目の動きを弱める、`downMax` を下げる） |
| 横を向くと、まつげが髪の上に乗って見える | まつげを、髪の上にも重ねていた（`lashOver` 1） | `lashOver` 0 |
| 撮影の道具が終わらない／`%TEMP%` にプロファイルがたまる | セキュリティソフトが、Chrome のプロファイルを消させない。消えるまで繰り返す作りだった | プロファイルを使い回す。待ちに上限 |
| 撮影で、PC が重い | ソフトウェア描画の Chrome を 4 つ並べていた | GPU で描く・優先度を下げる・2 つ |
| 正面の絵だけ、撮るたびに違う | 向きの指定が無いと、自動の視線・まばたきで動く | 正面にも `yaw=0` |
| 目のキーで「線が取れません」（`neon`。輪郭線を黒で描く絵柄） | 黒い輪郭線が「濃いまつげ」の色に入り、目尻のはねとつながって、コマのふちに触れる塊になる。眉も目のすぐ上で、まつげに入る | `keyshape.py` に `--dark-static`（細くコマのふちまで続く濃い線と、白目から離れた濃い塊を、動かない線にする） |
| 帯と白目の間に肌色のすき間、灰色のまだらが動かない（`neon`） | 白目の上の影（202,184,195）が少し赤く、白目の色の条件から外れた。白目の上のふち B が、影と白の境目の平らな線になった | `--white-shade` |
| 目尻のはねの中に肌色の点（`pink02`） | はねの中の赤みのある暗い影が、まつげの色の条件から外れ、帯の穴になった | `--lash-fill <面積>`（1500〜4000） |
| シートの目が大きく描かれた（`pink02`: 横 1.15・縦 1.3 倍）／にらみの目尻に白い四角 | 描かせた目の大きさが基準と違う／白目の端が縦にまっすぐ切れたキー | `key_eye_scale`／`key_eye_slope`（3.5） |
| つり目の瞳が丸く見え、上が帯に隠れない（`neon`） | 道具が、瞳を白目の開きのまん中に置く。元の絵は、瞳が上まぶたの下へ入り込む | `iris_dy`（測って −20）。`key_eye_dy` も同じ絵で（+4） |
| 歯が見える閉じた口で、口の開きが効かない／開く途中で歯が二重に透ける（`neon`） | 閉じた口のキーが「中が見える口」になり、表情が口を開けていると見なされた／中が見える口どうしを、重みのまま半々に溶かした | エンジンで閉じた口を判定から外した／`mouthKeySharp`（8）。重みがちょうど半々の点（開き 0.2）だけ、少し透ける |
| 母音の口の形のスライダーが、キーの形の口に効かない | スライダーは、式で描く口の値だった | エンジンを直した（開き・幅・上下の位置を、絵に掛ける。`keyMouthShapes`） |
| 右を向くと鼻が線になる（`neon`） | 鼻すじの軸が、顔の中心線を鼻の絵の中へ寄せた所 = 鼻の絵の左の端。右を向くと、鼻の全部が「向いた側の半分」として詰まった | `noseAxis` [左を向くとき, 右を向くとき]（`neon` [1506, 1539]。右は鼻の絵の右の端） |
| 下を向くと、口が大きく見える（`neon`） | 口の高さでの顔の幅は 2% しか細くならないが、あご先へ向かって細くなる顔の中で、口の幅だけが同じ | `tune.mouthDownSize`（0.8）・`mouthPitchBend`（0.3）。値は、比べの絵を見て決めた |
| ヘアピンが髪とずれる、ツノ（アンテナ）・ヘッドホンが曲がる（`neon`） | 髪飾りの全部を、`kurage02` の髪飾りの位置の 1 点で動かしていた。アンテナは、その点に付けて布として揺らしていた。ヘッドホンは顔の面に点ごとに沿わせていた | `pin_split`（ピンごとの層。留めている房に付く）、揺れ物の `frame`（固い板）・`type: rigid`（曲げずに回るだけ）・振り子の `stiff` |
